## 复现情况与抓取方式

目前没有已验证的稳定复现步骤。已知的观察条件是“晚上访问多时更容易失败”，尚不能确定流量是否为触发原因。站点地址、失败路径、请求方法、认证条件及客户端环境待补充。

接手后优先按以下方式捕获一次故障（待执行）：

1. 补齐站点和曾失败路径，用原访问方式观察；记录准确时间及时区、路径、方法、实际状态码、耗时、请求 ID 和目标实例（若可获取）。
2. 在同一窗口低频访问无副作用的静态页面和动态接口，记录失败及正常对照；标注是否命中缓存。不要将未测试路径记为正常。
3. 保存该窗口前后 5–10 分钟的代理访问日志、完整错误日志及应用日志，按请求 ID、时间、路径和 upstream 对齐。无法对应则记录“尚未确认属于同一请求”。

如需受控复现，先在测试环境设置并发上限与停止条件；当前未实施压力测试。

## 接手初查顺序

1. **先捕获一次故障并关联日志**：按上述字段留证；保留超时日志完整阶段描述，确认应用收到请求及响应完成情况。
2. **做路径和时段对照**：比较静态/动态、正常/故障窗口；确认链路后，从代理所在环境低频比较公网路径与直连应用路径，保持必要的 Host、协议和认证一致。
3. **采集现场指标**：请求量、并发、延迟、错误率；进程/容器状态和退出原因；CPU、内存、连接、文件描述符、队列，以及数据库池和依赖耗时。
4. **如需重启，先保存现场**：至少保留日志、进程状态及退出原因；记录重启对象、时间、恢复情况、恢复持续时间及是否复发。随后根据证据选择下一轮验证。
