## 已知现象与判断边界

- **待确认；证据位置：未提供原始记录**。原笔记观察“晚上访问多时更容易失败”：优先检查并发排队、应用执行槽位、数据库/外部接口等待，以及资源限制；不能据此认定机器容量不足。
- **待确认；证据位置：未提供原始记录**。原笔记观察“静态页面通常能打开”：若静态由 CDN 或 Nginx 直接提供，说明该路径可能正常；不能证明应用或整台服务器正常。先确认静态是否来自缓存。
- **待确认；证据位置：未提供原始记录**。原笔记观察“重启后暂时恢复”：可能清掉积压、连接、锁等待或异常进程，也可能暂时释放泄漏资源。必须明确重启的是应用、代理、数据库还是整台机器，以及恢复持续多久。
- **待确认；证据位置：未提供原始记录**。原笔记观察“偶有 `upstream timed out`”：需要整行日志判断发生在连接、等待响应头还是读取响应体阶段。超时常见于 504；观察到的 502 可能由其他错误、代理层或重试产生。以同一时间、请求 ID、路由和 upstream 的记录为准。

## 排查顺序

以下为待执行建议；没有现场验证记录，适用于本站的判断均待确认。每个条件分支只列验证方向，不表示条件已成立。

### 1. 先确定谁返回错误、哪些请求失败

画出实际链路：浏览器 → CDN/负载均衡（如有）→ Nginx/其他代理 → 应用 → 数据库/缓存/外部接口。

取一次故障的准确时间及其时区，查看前后 5–10 分钟各层日志。记录请求 ID、路由、实际状态码、目标实例及耗时。分别统计静态与动态路径的错误率、请求量、p95/p99 延迟；区分单个接口、单个实例和全站。不要只看平均耗时或一条日志。

### 2. 看完整代理错误，确定等待阶段

| 日志现象 | 优先核对 | 下一条关键证据 |
| --- | --- | --- |
| `while connecting to upstream` | 目标地址/端口、监听进程、连接队列、网络路径 | 应用是否收到请求；连接耗时是否升高 |
| `while reading response header from upstream` | 应用执行/排队、数据库/外部调用、线程或事件循环阻塞 | 应用入口时间、执行阶段耗时、工作进程占用 |
| 读取响应体时超时 | 响应生成、流式停顿、依赖或 I/O 等待 | 首个响应之后卡在哪个阶段 |
| `connection refused` | 进程退出、端口不匹配、重启窗口 | 进程/容器退出记录与监听状态 |
| `prematurely closed connection` / reset | 应用崩溃、worker 被杀、OOM、应用超时 | 应用异常、内核/容器终止原因 |

技术依据：[Nginx upstream 文档的 `$upstream_addr`、`$upstream_status`、各阶段耗时变量](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#variables)。本站是否使用该配置待确认，需维护者提供实际配置位置。

同一次请求可能重试多个 upstream；地址、状态、耗时字段可能是多值，不能只取最后一个。

若使用 Nginx，现有访问日志缺少耗时时，可在计划内补充以下字段：
`$time_iso8601 $request_id $request_method $uri $status $request_time $upstream_addr $upstream_status $upstream_connect_time $upstream_header_time $upstream_response_time`。
让请求 ID 传到应用并写入日志；若已有统一追踪 ID，沿用它。记录路由时避免保存含 token 的查询参数。改日志配置应先验证语法，再 reload。

### 3. 在重启前采集故障现场

尽量在故障仍存在时，用 1–2 分钟采集；若必须立即恢复，至少先保存日志、进程和退出原因。

- 应用：各实例的存活状态、工作进程数量、忙闲/排队请求、线程栈或任务栈（使用框架支持的诊断方式）、请求耗时分段。
- 系统/容器：CPU、RSS 内存趋势、GC、swap、磁盘空间及 I/O 等待、文件描述符、连接数、容器 CPU 限流、OOM/退出码。低 CPU 也可能是等待或执行槽位耗尽。
- 数据库/缓存：连接池在用/空闲/等待数、获取连接耗时、慢查询、锁等待、长事务、连接限制。应用池排队与数据库自身忙碌要分开看。
- 外部依赖：延迟、错误、调用超时、重试次数；检查是否出现请求越慢、在途越多、重试进一步放大负载的循环。
- 保留重启前后的同一组指标，并记录重启对象及恢复时长。

### 4. 从代理所在环境做小规模路径对照

用无副作用的轻量接口，以低频请求比较：公网动态接口、代理直连应用、应用轻量健康接口、会访问数据库的代表接口。保持必要的 Host/协议/认证一致，避免因路径差异误判；不要为了诊断开放应用公网端口。

- 直连应用也慢：重点向应用及依赖收敛。
- 直连稳定但代理失败：检查代理到应用的地址、连接、超时、实例分配及额外代理层。
- 轻量接口正常而数据库接口慢：重点检查数据库执行和连接池等待。
- 只有某个实例失败：比较该实例日志、资源趋势、配置与部署版本。

健康接口成功只代表该接口经过的链路；不能据此宣布服务正常。

### 5. 用趋势区分“峰值触发”和“积累触发”

- 若错误紧随并发/慢依赖上升，并且工作槽位或池等待持续满：调查排队、慢操作、阻塞与重试。
- 若在相近流量下，RSS、FD、连接或池占用随运行时间增加，重启后归零：调查泄漏及未释放资源。
- 若固定夜间时段出现：检查备份、批处理、定时任务、日志处理及部署时间。
- CPU/内存/池限制只有与同一故障窗口的耗时、队列和错误相关联，才能成为根因证据。

每轮只改变一个主要因素，用相近流量下的错误率、p95/p99、队列/池等待和资源趋势验证。受控复现优先在测试环境做，设置并发上限和停止条件。

## 目前最缺的信息

建议先收集以下五项，再评估是否足以决定下一步（待执行）：

1. 部署链路和技术栈：是否有 CDN/负载均衡、代理类型、应用框架、进程/容器数量、数据库类型。
2. 一次具体故障时间、失败路由及完整代理错误日志；同窗口访问日志和应用日志（脱敏）。
3. 重启的具体组件、重启前运行多久、恢复持续多久。
4. 峰值请求量/并发、延迟和错误率；重启前后的 CPU、内存、连接、进程/容器退出记录。
5. 代理/应用/依赖的超时与重试配置、工作进程数、数据库池大小及等待指标；近期代码或配置变更。

## 什么证据才支持调整

以下均为待验证的调整条件，本站尚无对应证据；结论待确认，不能视为已获准或已完成的调整。

- 确认慢查询或锁等待 → 优先处理查询、索引、事务和竞争。
- 确认连接/资源未释放 → 修复释放路径，验证运行时间增长时资源稳定。
- 确认阻塞或执行槽位排队 → 处理阻塞任务、并发控制和队列；配置变更要验证下游承载。
- 确认重试放大 → 收紧超时预算与重试，评估幂等性和退避。
- 超时调整应基于合理请求时长与整条链路预算。Nginx 的 `proxy_read_timeout` 限制的是相邻两次读取之间的等待，并非整个响应总时长（证据位置：[官方指令说明](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_read_timeout)）；单纯延长可能让在途请求积压更多。
- 只有确认正常业务负载持续达到真实资源瓶颈，并排除慢操作、泄漏、异常排队等因素后，再讨论扩容或容量调整。
