# 投递前一页检查清单

适用：校园活动报名网站（社团报名项目为同一项目）｜整理：2026-10-08

**结论：已有简历、邮件和口述材料基本守住事实边界，可以保留。** 下列“风险表述”是发送前排查用的反例，并非现有正文已经写错。这里的支持来自用户事实记录及已有材料，尚未独立核验项目代码、测试日志或运行效果。

## ① 有支持，可以保留

- [ ] 项目名称统一；写“参与开发校园活动报名网站”，个人职责为报名接口、名额限制和邮件通知，技术栈为 Node.js、SQLite。[事实底稿](参考方法与事实记录.md)
- [ ] 验证范围准确：名额限制只测过普通报名，未做并发验证；“测过”不扩写成“所有测试通过”。[面试笔记](社团报名项目面试笔记.md)
- [ ] 状态一致：尚未正式上线，暂无性能测试数字；周末试用邀请未发送、试用待执行。[试用准备](周末试用邀请与准备清单.md)

## ② 容易说大：若出现，直接替换

| 风险表述 | 事实缺口 | 具体替换写法 |
| --- | --- | --- |
| “独立完成整套后端系统” | 只确认三项职责，无完整分工或贡献比例 | “参与后端开发，负责报名接口、名额限制和邮件通知。” |
| “解决高并发，保证不会超额” | 未做并发验证，检查与写入机制未核实 | “负责名额限制，已测过普通报名；多人同时报名时的名额处理尚待验证。” |
| “实现可靠邮件通知，失败自动重试” | 触发、失败处理、重试与送达结果未核实 | “负责邮件通知功能；具体触发与失败处理需对照代码确认。” |
| “显著提升报名效率，减少人工统计” | 无旧流程、耗时对比或真实使用记录 | “项目面向校园活动报名，我负责报名接口、名额限制和邮件通知；实际使用效果尚待验证。” |
| “同学普遍反馈好用，流程顺畅” | 尚未找同学实际试用，无用户原话 | “计划邀请两位同学尝试模拟报名，记录入口、提交和结果理解中的卡点；试用尚未执行。” |
| “主导 SQLite 选型，降低部署成本” | 决策人、当时理由及成本收益无记录 | “项目使用 SQLite；当时的选型理由还需回查记录。” |

“完善参数校验”“防止重复报名”“使用事务、锁、队列”等也须核对代码后再写。技术的一般优点不能证明自己做过，也不能证明本项目取得了效果。[选型边界](SQLite选型_一分钟回答与事实边界.md)

## ③ 投递前最后核对

- [ ] **补齐发送信息：**姓名、学校专业、联系方式、项目起止时间、到岗日期、实习时长及每周天数；核对公司和岗位，实际附上简历。校园产品公司的定向消息中，“你们在做校园产品”须有招聘信息或公司介绍支持。
- [ ] **准备可追问依据：**优先回查三项职责对应代码，以及普通报名的版本、输入、预期和实际结果。没有资料就保留验证边界，不用猜测补成经历。
- [ ] **计划与成果分开：**补并发测试、试用、改进和复测均按实际状态写。两人试用即使完成，也只支持该版本、该任务下的观察，不能证明普遍好用或效率提升。
- [ ] **价值说到证据为止：**保留校园活动报名这一场景，让读者看懂自己负责哪一步；现有材料没有反复发生的用户抱怨、旧流程代价或效果对比，不补写成已验证痛点。

**可直接用于简历的正文：**参与开发校园活动报名网站，使用 Node.js 和 SQLite，负责报名接口、名额限制和邮件通知。名额限制目前仅测过普通报名，尚未进行并发验证；项目尚未正式上线。
