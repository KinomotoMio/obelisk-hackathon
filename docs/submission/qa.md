## 真实性与可信度

### 上报的调用量和顺利率能造假吗？（C1，待讨论；C6、C10）

**能，我们不回避。** 场景和结果由用户本机的 AI 编程助手判断，再由用户签名上报，改了本机程序就能改结果。

现在能保证的：

- 每次上报都由用户钱包签名，链上按版本、按钱包去重，同一个钱包重复报不会多算钱包数；
- 调用按 Skill 正文的内容指纹对应到铸造的版本，换了内容就不是同一个版本；
- 事实信号（工具报错、用户纠正、反复编辑、重复调用）按规则直接计数，和 AI 的判断分开存、分开展示。

现在保证不了的：本机程序没有被改动；两个钱包不属于同一个人（C10）。想刷量就要真的去跑 AI 任务，成本比买安装量高，但不是不可能。赛后的候选方向（区分服务能记录的取回次数和本机自报的数据、交叉验证、按信誉加权、抽样复核）见 [C1](../vision/10-challenges.md#c1--顺利率在本机算上报可以被篡改)，都还没有采用。

### 演示数据是不是编的？（C8，已认可）

分三种，页面上都有标注：

- `/market` 和 Skill 页上的调用量、钱包数、场景、族谱读自链上，是真实操作产生的，交易都能在浏览器上查到；
- `/market/stage-2` 的价格、分成比例、收入标着「示例」，阶段 2 才实现；`/preview` 目前标着「示意内容」；
- 第 5 步的对比数据计划由 Playground 产生：模拟用户，但 AI 运行、加密和交易都是真的，每次运行有出处记录，`/runs/<运行编号>` 逐笔核对交易。**这批数据还没有跑**，演示时`待填`实际情况。

出处记录能说明数据是怎么产生的，但不能证明本机程序没有被改动，这一点和 C1 相同。

### 顺利率不就是 AI 猜的吗？（C14，待确认）

是推断，所以和事实分开。事实信号直接统计；「顺利 / 有返工 / 失败 / 无法判断」是 AI 判断，无法判断的不进分母；用「顺利率」不用「成功率」；一个场景不到 5 次可判断的调用，页面显示「样本不足」而不是百分比。

### 作者把描述写得很宽怎么办？（C5，已认可）

我们不看描述，看证据。Skill 页把作者声明的场景和实测场景并排，每个实测场景有自己的调用次数和顺利率，和作者声明一致的标「作者声明」，夸大了多少一眼可见。

## 为什么上链

### 为什么要上链，自己的服务器不行吗？（C4，已认可）

存在自己服务器里，规则、衍生关系、分成都可以被平台改。写在链上：

- 分享规则和打开回执任何人可查，包括我们在内都无法私自改写；
- 身份和成绩记在用户自己的钱包地址下，换平台也带得走；
- 族谱公开，阶段 2 的分成可以由链上程序在付款时执行。

链上只放规则、回执、指纹、计数和场景标签，不放 session 和 Skill 的内容。四个合约和测试网地址见 [主网材料](mainnet.md)。

### 用户需要买币吗？

不需要。用户在本机签名，在线服务的代付钱包提交交易并付手续费，所以浏览器上看到的发送方是代付钱包，方法名是 `…BySig`。主网上一笔代付约 0.004 BOT（[#5](https://github.com/KinomotoMio/obelisk-hackathon/issues/5) 的估算）。

### 主网部署了吗？

`待填`（按提交时的实际情况回答）。撰写时没有：等主办方发放主网 BOT；代码和测试网完全一样，切换步骤已经写好并在测试网演练过源码验证（[#5](https://github.com/KinomotoMio/obelisk-hackathon/issues/5)、[mainnet.md](mainnet.md)）。

## 隐私

### 分享出去的 session 安全吗？服务能看到内容吗？（C11，待确认；C3，已认可）

- 内容在发送方电脑上加密后才上传，在线服务只存密文，看不到内容；接收者在浏览器里用钱包解密（X25519、HKDF、AES-GCM，浏览器自带的 WebCrypto）；
- 发送前有隐私体检和打码，覆盖常见格式（路径、密钥、邮箱等），对话里只显示检出项的类型和位置，不显示原值。但它**不保证查全**；
- 钥匙包由在线服务按链上规则放行，这一步需要信任我们的服务（C11）；
- 接收者看完可以截图、抄写，技术上防不住（C3）。我们做的是让泄露可以追溯：整页印着接收者地址的水印。看不见的指纹是阶段 2。

### 让 AI 判断场景和结果，会不会把 session 发出去？费用谁出？（C12，待确认；C7，已认可）

判断用的是用户自己本机的 Codex（优先）或 Claude Code，和平时用它一样，额度也是用户自己的，我们不接任何托管的模型服务。每次调用只发约 5,000 字符的切片，不发成功的工具输出，也不发 Skill 正文；先预览要读什么、跑几次，确认后才运行。离开本机的只有场景标签和计数，会话文本和判断理由都留在本机（[#25](https://github.com/KinomotoMio/obelisk-hackathon/issues/25)）。

### 链上的记录会暴露什么？

钱包地址、分享编号、内容指纹、打开次数、调用计数和场景标签。不包含对话内容、文件名或 Skill 正文。

## 赛前与比赛期间

### 哪些是赛前就有的？

Obelisk 的本地索引、检索、记忆和桌面 App 的原有部分是赛前就有的开源项目（[tommy0103/obelisk](https://github.com/tommy0103/obelisk)，AGPL-3.0）。分界点是 `b5a7696`（2026-09-18）：之前 189 个提交，比赛期间 208 个，第一个在 2026-10-07 01:17。合约、在线服务、公开网页、Playground、分享、Skill 资产、使用统计、履历都是比赛期间写的；索引本身没有改动。详见 [赛前已有与比赛期间新增](before-and-during.md)，文末有复核命令。

### 你们和 Obelisk 原项目是什么关系？

`待填`（团队成员与上游维护者的关系，由 owner 说明）。可以确定的事实：本仓库是 Obelisk 的 fork，比赛分支 `hackathon` 不包含上游在分界点之后的 22 个提交；链上和在线服务的代码是否进入上游，还没有和维护者确认（[路线图 · 待决策](../vision/07-roadmap.md#待决策) 第 6 条）。

### 这和 Obelisk「对话是证据，不是答案」的立场矛盾吗？（C15，已认可）

不矛盾。检索层仍然不替你下结论、不给判断排序；顺利率和能力维度属于产品层，服务于具体场景：买家要知道 Skill 在自己的场景下好不好用，招聘方要看到可以核对的能力证据。

## 市场与商业

### 和 skills.sh 这样的 Skill 市场有什么不同？（C13，待确认）

互补。skills.sh 解决分发，排行榜基于匿名安装统计；我们提供它没有的：真实调用量、实测场景和顺利率，以及归属、族谱，阶段 2 加上分成。免费 Skill 以后可以从 Obelisk 发布到 skills.sh。

### Skill 正文一被调用就能复制，凭什么收钱？（C9，待确认）

我们不卖文本。复制走的只是一份快照；持续更新、合法使用的授权凭证、真实使用证据和原始上下文复制不走。详见 [05](../vision/05-market-and-revenue.md#skill-正文可以复制价值从哪里来) 和 `/market/stage-2` 的 M6 一节。「经验数据授权」团队还没有确认是否这样讲。

### 钱从哪里来？现在有收入吗？

现在没有，上架、付费、分成、收入都是阶段 2，`/market/stage-2` 只是标明示例的预览。设想见 [05 · 市场与收益](../vision/05-market-and-revenue.md)：买家为 Skill 和上下文付费，收入沿族谱分给上游作者；AI 公司按经过 Obelisk 的取用量付费（阶段 3）。

### 有真实用户吗？

还没有赛外的真实用户，路线图把它放在阶段 2。比赛期间做了两轮队内测试（[第 1 轮](../testing/round-01.md)、[第 2 轮](../testing/round-02.md)），测试网上的数据就来自这些真实操作。参与人数：`待填`。

## 技术细节（被追问时）

| 问题 | 回答 |
| --- | --- |
| 支持哪些 AI 编程助手？ | 检索支持 Claude Code、Codex、DeepSeek Harness、Kimi Code、OMP、Pi（赛前已有）。新功能在 Claude Code 和 Codex 里都能用：App 复制的 prompt 可以选目标；判断优先用 Codex；Playground 主要用 Codex 跑。已知缺陷：Codex 的 Skill 调用识别会漏记或重复记（[#38](https://github.com/KinomotoMio/obelisk-hackathon/issues/38)、[#39](https://github.com/KinomotoMio/obelisk-hackathon/issues/39)），所以调用和上报建议在 Claude Code 里做 |
| 为什么命令行优先，App 只复制 prompt？ | 所有操作都在用户自己的 AI 编程助手里说一句话完成，每一步先预览、再确认；App 只负责展示，不替用户签名或上链。见 [设计原则](../vision/README.md#设计原则) |
| 场景标签是固定的吗？ | 带版本号的公共词表，第一版 45 个标签、5 个维度；AI 优先从词表里选，确实没有合适的才新建（C16）。新建的标签目前只记在本机，跨用户汇总是赛后的事（[#40](https://github.com/KinomotoMio/obelisk-hackathon/issues/40)） |
| 场景很多时，一笔交易放得下吗？ | 一个版本的桶超过 32 个时自动拆成几笔上报，中断后重跑只发剩下的部分（[#25](https://github.com/KinomotoMio/obelisk-hackathon/issues/25)） |
| 趋势图按什么时间统计？ | 按服务收到上报的时间分周，不是按调用发生的时间，页面上已注明 |
| 测试怎么做的？ | 合约、服务、CLI、App 的测试都在仓库里，用本地 Hardhat 链和假的 AI 助手，不连真实的在线服务。CI 配置包含合约和服务的测试，但只在 PR 和 `main` 上触发，`hackathon` 分支的推送不会自动运行，验收靠各 issue 的完成评论里记录的命令 |
